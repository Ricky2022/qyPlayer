# 阶段 0 报告

本报告记录阶段 0（仅 Web）的实现情况、实测数据、发现的问题和待决事项。对应需求见 [PRD](./PRD.md)。

## 1. 结论

| 问题 | 结论 |
| --- | --- |
| 自建 Canvas 2D 时间线渲染器可行吗？ | **可行**。1080p 下 60 帧每秒无掉帧，单次绘制的 CPU 耗时中位数 0.2 毫秒。仅在桌面 Chromium 上验证，移动端未测。 |
| 包格式和安全校验能落地吗？ | **能**。13 个一致性测试包（3 合法、10 非法）全部符合预期，非法包都被拒绝并给出明确原因。 |
| 音频主时钟方案可用吗？ | **可用**。时钟与音频位置的偏差在 0.02 到 0.06 秒，满足 T-12（100 毫秒）。输出设备延迟未计入。 |
| 本地转码路线（WebCodecs）可行吗？ | **有条件**。本机 H.264 编解码、HEVC 解码、AAC 编码都报告支持；**HEIC 在 Chromium 中不能直接解码**，需要另行解决（见 5.3）。 |
| 能进入阶段 1 吗？ | **可以**。5.1 的入场与转场时序问题已决定并修正（见 5.1 结论）。 |

### 4.4 实测数据

示例包：横屏 `sample-16x9`（30.4 秒、5 页，含 1 段视频和 3 个多图页）、竖屏 `sample-9x16`（40 秒、7 页）。完整播放一遍，同时统计每帧间隔。

| 指标 | 横屏 | 竖屏 |
| --- | --- | --- |
| 帧率（帧每秒） | 59.98 | 59.96 |
| 帧间隔 p50 / p95 / 最大（毫秒） | 16.7 / 16.8 / 17.3 | 16.7 / 16.8 / 16.9 |
| 间隔超过 25 毫秒的帧数 | 0 | 0 |
| 单次绘制 CPU 耗时 p50 / p95 / 最大（毫秒） | 0.2 / 1.2 / 6.1 | 0.2 / 0.5 / 4.7 |
| JS 堆（MB） | 24 | 39 |

“单次绘制耗时”只含 `stateAt`、`renderFrame` 和同步逻辑的主线程时间，不含 GPU 光栅化；GPU 侧压力由“帧间隔没有超过 17.3 毫秒”间接体现。

拖动定位耗时（从 `seek()` 到画面就绪；每次先回到 0 秒再跳转，素材近似冷加载；每格 8 次，单位毫秒）：

| 目标 | 横屏 p50 / p95 | 竖屏 p50 / p95 |
| --- | --- | --- |
| 三图页（需读取并解码 3 张图） | 90.6 / 100.6 | 101.6 / 129.0 |
| 视频页（需 seek 视频） | 77.2 / 139.5 | 110.4 / 175.9 |

视频页起点附近，视频比应有位置慢 0.07 到 0.17 秒（上一页没有预先定位视频时是 0.17 秒，加了预定位后顺序播放是 0.07 秒；直接跳到视频页前 0.3 秒处仍有约 0.15 秒）。这在 0.3 秒的校正阈值内，不会被重复校正。

## 5. 发现的问题与建议

### 5.1 入场动画与转场串行，多图页出现空画面（需要你决定）

PRD 8.3 规定“入场动画在转场结束后开始”，所以每个元素在自己的入场延迟之前不可见。后果（横屏示例包实测，`stateAt` 输出）：

| 页 | 转场 | 转场开始后 0 / 0.3 / 0.6 / 0.8 / 1.0 秒，本页可见图层数 |
| --- | --- | --- |
| p001（第一页，3 图） | fade 0.6 秒 | 0 / 0 / 0 / 2 / 3，开头 0.6 秒是黑屏 |
| p004（3 图） | slide 0.6 秒 | 0 / 0 / 1 / 1 / 3，转场的 0.6 秒内新页是空的，只有上一页滑出去 |

也就是说切到多图页时，先出现 0.6 秒的空画面，再一张张冒出来，和苹果“精选集”那种“新页随转场进来”的观感不一致。同时拖动进度条到某页的开头，看到的是空页。

可选方案：

- **A（推荐）**：入场延迟从页开始计时而不是转场结束。转场期间各元素按自己的延迟陆续进入，没有空档。改动只在 `core` 的时间线和生成器（延迟取值），格式不变。
- **B**：保持串行，但多图页的转场只用 fade 且持续时间缩短，空档变成短暂的淡入。效果保守。
- **C**：保持现状，接受空档。

**结论（2026-11-18）：已采纳方案 A。** 引擎本来就把 `enter.delay` 当作相对页开始的时间，空档来自生成器把转场时长加进了延迟；现已改为从 0 起按 0.15 秒错开，PRD 8.3 同步改写。上表是改动前的数据。

### 5.2 其他已确认的问题

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| A-05 未实现 | 无配乐时连续视频页切换可能爆音 | 阶段 1 为视频原声加短淡入淡出 |
| t=0 是空画面（第一页的 fade 加元素延迟） | 暂停在开头时是黑屏；列表缩略图也需要封面 | 方案 A 能缓解；另可约定用 `cover` 或第一页最终画面作开屏海报 |
| fade、zoom 转场按透明度直接叠加，中点画面略暗 | 观感略有“呼吸”，不严重 | 可改为新页不透明度直接 0→1、旧页保持，或用加法混合。阶段 1 目视评估后再定 |
| 视频页起点有 0.07 到 0.17 秒滞后 | 听不出，但画面与时间线略有偏差 | 已加预定位；彻底解决需要预解码，阶段 1 再看 |
| 读取视频时把整个文件读入内存 | 8 秒、8 Mbps 的片段约 8 MB，没有问题；长视频或手机上会吃紧 | 阶段 1 评估 `MediaSource` 或在导出时只保留用到的片段（PRD 已有 F-PKG-02） |
| 体积上限检查用的是 ZIP 目录里**声明**的大小 | 声明值可被伪造 | 阶段 1 在 `readBlob` 增加“实际字节数不超过声明值”的断言；未验证 zip.js 对此的行为 |
| Ajv 校验器在运行时用 `new Function` 生成代码 | 在 Tauri 等严格 CSP（不允许 `unsafe-eval`）下会失败 | 阶段 1 改用 Ajv 的独立编译（standalone），预先生成校验函数。**未在 Tauri 中验证** |

### 5.3 能力矩阵（本环境）

| 能力 | 结果 |
| --- | --- |
| WebCodecs 解码：H.264 / HEVC / VP9 / AV1 | 全部报告支持 |
| WebCodecs 编码：H.264 / HEVC / VP9 / AV1 | 全部报告支持 |
| WebCodecs AAC 解码、编码，MP3 解码 | 支持 |
| `ImageDecoder`：JPEG / PNG / WebP / AVIF | 支持 |
| **`ImageDecoder`：HEIC / HEIF** | **不支持** |
| `<video>` / `<audio>` 播放：H.264+AAC、HEVC、VP9、AV1、MP3、AAC | 全部 `probably` |
| `OffscreenCanvas`、`createImageBitmap`、`requestVideoFrameCallback`、全屏 API | 都有 |

局限：`isConfigSupported` 只表示“声称支持”，**没有用真实的 HEVC、HEIC 文件做解码测试**（没有找到可再分发的样本）。HEVC 在 Windows 上通常依赖显卡硬件解码或系统扩展，不同机器会不同。

对 R-01、R-06 的含义：

- HEIC 在 Chromium 里不能直接用，F-IMP 要支持 iPhone 照片就需要二选一：引入 libheif 一类解码库（LGPL，见 R-06），或在 Tauri、Capacitor 套壳里调用平台原生解码。这需要在阶段 1 前定下来。
- 视频导出用 WebCodecs 编码 H.264 在本机可行；其他浏览器和 WebView 未测。

## 8. 如何复现

```bash
pnpm install
pnpm test                    # 全部单元测试
pnpm typecheck
pnpm fixtures:fetch          # 下载示例素材（Wikimedia 会限流，脚本会自动退避）
pnpm fixtures:check          # 检查素材来源记录
pnpm fixtures:build          # 构建 fixtures/build 下的 3 个示例包
pnpm fixtures:conformance    # 重新生成 fixtures/conformance
pnpm --filter @qyplayer/web dev
```

- 播放器：`http://localhost:5173/`，拖入 `.qyp`；开发时加 `?demo` 会自动打开程序生成的演示包。
- 渲染器试验页：`/playground.html`（`?m=portrait` 看竖屏）。
- 实测页：`/bench.html`，选择 `.qyp` 后点“运行”；**测量前确保浏览器窗口可见并在前台**。
